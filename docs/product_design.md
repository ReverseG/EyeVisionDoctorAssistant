# 眼底 AI 辅助诊断系统产品设计文档

> 辅助诊断参考，不替代医生最终诊断
> 文档版本：v2.0
> 最后更新：2026-04-02

## 1. 文档目标

本文档作为一期建设的统一基线，用于对齐产品、架构、算法、前后端、测试与合规团队。

本文档重点回答以下问题：
- 一期到底做什么，不做什么
- 系统中的核心对象与业务流程是什么
- AI 结果如何进入医生审核与报告闭环
- 研发如何按阶段交付并验收
- 医疗 AI 场景下最基本的合规与可追溯要求是什么

## 2. 产品定位

### 2.1 产品名称

眼底 AI 辅助诊断系统（EyeVision AI）

### 2.2 产品定位

面向医院眼科、体检中心和专病筛查场景的眼底影像辅助诊断平台，支持眼底彩照与 OCT 图像分析，帮助医生提高筛查效率、结果一致性和随访管理效率。

### 2.3 产品原则

- 所有 AI 输出必须以“辅助诊断参考”形式呈现
- 报告签发责任属于医生，系统只提供分析与辅助建议
- 所有关键结论必须可回溯到原始图像、模型版本和审核记录
- 一期聚焦可上线、可审计、可扩展，不追求一次性做全

## 3. 版本范围

### 3.1 一期目标（MVP）

一期聚焦医院内 Web 端闭环，范围如下：

- 患者档案管理
- 检查单创建与图像上传
- 眼底彩照 AI 分析
- OCT AI 分析
- 图像质量评估
- AI 结果展示与热力图查看
- 医生审核与结果确认
- 结构化报告生成与导出
- 随访建议与随访计划创建
- 审计日志与模型版本追溯

### 3.2 一期不做

以下内容不进入一期承诺范围：

- 小程序、移动 App、微信集成
- 面向患者的自助端
- 多院区 SaaS 多租户能力
- 自动签发报告
- 复杂多模态关联评分上线决策
- 面向生产的联邦学习、主动学习平台
- 与 HIS/EMR/LIS 的深度双向集成

### 3.3 二期预研项

- 医生报告症状抽取
- 图像与症状的统计关联分析
- 多中心数据接入
- 灰度发布与模型漂移监控
- HIS/EMR/LIS 标准接口对接

## 4. 目标用户与角色

### 4.1 业务用户

- 眼科医生：审核 AI 结果、编辑并签发报告、制定随访计划
- 技师/护士：创建检查、上传图像、维护基础信息
- 科室管理员：用户管理、模板配置、统计查看
- 医学顾问/质控人员：抽检模型结果、复核异常样本

### 4.2 系统角色权限

| 角色 | 患者档案 | 创建检查 | 查看 AI 结果 | 审核结果 | 编辑报告 | 签发报告 | 系统设置 |
|------|----------|----------|--------------|----------|----------|----------|----------|
| 医生 | 是 | 是 | 是 | 是 | 是 | 是 | 否 |
| 技师/护士 | 是 | 是 | 部分 | 否 | 否 | 否 | 否 |
| 管理员 | 是 | 是 | 是 | 否 | 否 | 否 | 是 |
| 质控人员 | 脱敏查看 | 否 | 是 | 否 | 否 | 否 | 否 |

## 5. 核心业务场景

### 场景 1：新建检查并完成 AI 分析

1. 技师选择患者或新建患者
2. 创建检查单并上传左眼/右眼图像或 OCT 数据
3. 系统执行文件校验、质量评估和去重检查
4. 合格样本进入 AI 分析任务队列
5. AI 返回结构化结果、可视化结果和模型元数据
6. 系统将检查状态更新为“待医生审核”

### 场景 2：医生审核并签发报告

1. 医生打开待审核检查
2. 查看原图、热力图、病变统计、AI 置信度和提示信息
3. 医生执行“确认 / 修改 / 驳回重检”
4. 系统生成报告草稿
5. 医生补充诊断意见和随访建议
6. 医生签发报告，系统冻结报告版本

### 场景 3：随访管理

1. 系统根据疾病类型、分级和医生建议生成默认随访计划
2. 医生确认或修改随访周期
3. 后台任务生成待随访提醒
4. 历史检查支持同患者纵向对比

## 6. 核心领域模型

为保证前后端、算法和报表对齐，一期统一采用以下核心对象。

| 实体 | 说明 | 关键字段 |
|------|------|----------|
| Patient | 患者主档 | patient_id, name, gender, birth_date |
| Encounter | 就诊或筛查上下文 | encounter_id, source, department |
| Examination | 检查单 | exam_id, patient_id, exam_type, status |
| ImageAsset | 原始影像与派生文件 | asset_id, eye_side, format, storage_key |
| AnalysisJob | AI 异步任务 | job_id, exam_id, algorithm_type, status |
| AnalysisResult | AI 结构化输出 | result_id, job_id, model_version, summary |
| DoctorReview | 医生审核记录 | review_id, decision, reviewer_id, review_at |
| Report | 报告实体 | report_id, version, status, signed_at |
| FollowupPlan | 随访计划 | followup_id, due_date, risk_level |
| AuditLog | 审计记录 | event_id, actor, action, resource_id |
| ModelVersion | 模型版本元数据 | model_version, task_type, threshold_set |

## 7. 状态机设计

### 7.1 检查单状态

| 状态 | 含义 | 可触发动作 |
|------|------|------------|
| CREATED | 已创建，未上传完成 | 上传图像、取消 |
| UPLOADING | 上传中 | 重试上传 |
| UPLOADED | 上传完成，待校验 | 质检 |
| QA_FAILED | 图像不合格 | 重新上传、终止 |
| QUEUED | 已进入分析队列 | 取消分析 |
| ANALYZING | AI 推理中 | 查看进度 |
| ANALYZED | AI 完成，待审核 | 查看结果、重跑分析 |
| REVIEWING | 医生审核中 | 确认、修改、驳回 |
| REVIEW_REJECTED | 医生驳回 | 重检、补传 |
| REVIEW_CONFIRMED | 审核通过 | 生成报告 |
| REPORTED | 报告已签发 | 下载、归档、随访 |
| CLOSED | 流程结束 | 只读查看 |

### 7.2 报告状态

| 状态 | 含义 |
|------|------|
| DRAFT | 系统草稿 |
| EDITING | 医生编辑中 |
| PENDING_SIGN | 待签发 |
| SIGNED | 已签发 |
| VOIDED | 已作废 |

## 8. 功能范围拆解

### 8.1 患者与检查管理

- 患者主档创建、编辑、检索
- 检查单创建、取消、查看历史
- 同患者历史检查纵向展示
- 检查类型支持：眼底彩照、OCT、联合检查

### 8.2 影像处理与质量控制

- 上传格式校验：JPG/PNG/DICOM
- 图像去重与基本完整性校验
- 质量评估：清晰度、曝光、视野范围、遮挡
- 不合格样本进入 `QA_FAILED`
- 所有图像保留原始文件与处理后版本

### 8.3 AI 分析

一期支持以下任务：

- 眼底彩照 DR 分级
- 病变检测：微动脉瘤、出血点、硬性渗出、软性渗出
- OCT 分层与关键参数量化
- 黄斑水肿相关指标计算

AI 输出必须包含：

- 结构化字段
- 置信度
- 热力图或病变标注
- 模型版本
- 推理时间
- 阈值版本

### 8.4 医生审核

- 医生查看原图与可视化结果
- 审核结论：确认、修改、驳回重检
- 记录人工修改项与原因
- 审核动作写入审计日志

### 8.5 报告与随访

- 根据模板自动生成报告草稿
- 医生补充诊断结论和建议
- 导出 PDF
- 根据规则生成默认随访计划
- 支持后续随访结果回看

## 9. 非功能需求

### 9.1 性能目标

- 单次图像上传接口 P95 < 3s（不含大文件传输时间）
- 单张眼底图像推理耗时目标 < 10s
- 单个检查完整分析结果返回目标 < 60s
- 报告生成耗时 P95 < 5s

### 9.2 可用性目标

- 业务服务可用性 >= 99.5%
- AI 推理失败支持自动重试 1 次
- MinIO、PostgreSQL 支持备份与恢复

### 9.3 可观测性目标

- 请求链路日志
- 任务队列监控
- 推理耗时监控
- 错误码统计
- 模型版本调用统计

## 10. 系统架构基线

### 10.1 一期建议架构

```text
Web Frontend (Vue 3)
    ↓
API Service (FastAPI)
    ↓
Domain Services
  - Patient Service
  - Examination Service
  - Analysis Orchestrator
  - Report Service
  - Followup Service
    ↓
Infrastructure
  - PostgreSQL
  - Redis
  - MinIO
  - Celery/RabbitMQ
  - AI Inference Service
```

### 10.2 一期技术选型

| 层级 | 选型 | 说明 |
|------|------|------|
| 前端 | Vue 3 + TypeScript + Vite | 满足 Web 端交互 |
| 后端 | FastAPI + SQLAlchemy | 快速交付且适合异步接口 |
| 数据库 | PostgreSQL | 主业务库与审计元数据 |
| 缓存 | Redis | 会话、短期缓存、任务状态 |
| 对象存储 | MinIO | 原始图像、热力图、报告文件 |
| 队列 | Celery + RabbitMQ | 异步推理与通知 |
| AI 推理 | Python Service / Triton | 一期可先单服务，二期再扩展 |
| 监控 | Prometheus + Grafana | 指标监控 |
| 日志 | Structlog + ELK | 检索与审计分析 |

### 10.3 当前不建议在一期强依赖的组件

- MongoDB
- Elasticsearch
- 小程序 / App 网关层
- 多套推理框架并存

这些能力可在二期按容量和检索需求再引入。

## 11. API 设计原则

### 11.1 总体原则

- 推理接口采用异步任务模型，不同步返回最终报告
- 所有写接口要求幂等键
- 所有响应带 `trace_id`
- 重要结果带 `model_version` 与 `threshold_version`

### 11.2 核心接口

#### 创建检查

```http
POST /api/v1/examinations
```

请求示例：

```json
{
  "patient_id": "P00001",
  "exam_type": "fundus",
  "encounter_id": "EN20260402001"
}
```

#### 上传影像

```http
POST /api/v1/examinations/{exam_id}/assets
```

#### 发起分析

```http
POST /api/v1/examinations/{exam_id}/analysis-jobs
```

请求示例：

```json
{
  "analysis_types": ["dr_grading", "lesion_detection"],
  "requested_by": "U1001"
}
```

响应示例：

```json
{
  "job_id": "JOB20260402001",
  "status": "QUEUED",
  "trace_id": "8ec7f4..."
}
```

#### 查询分析结果

```http
GET /api/v1/examinations/{exam_id}/analysis-results
```

响应示例：

```json
{
  "exam_id": "E20260402001",
  "status": "ANALYZED",
  "model_version": "dr-v1.0.3",
  "threshold_version": "dr-th-202604",
  "summary": {
    "left_eye": {
      "dr_grade": 2,
      "confidence": 0.87
    },
    "right_eye": {
      "dr_grade": 1,
      "confidence": 0.92
    }
  },
  "lesions": [
    {
      "eye_side": "left",
      "type": "microaneurysm",
      "count": 12,
      "confidence": 0.92
    }
  ],
  "visualization": {
    "heatmap_url": "/objects/heatmaps/..."
  }
}
```

#### 提交医生审核

```http
POST /api/v1/examinations/{exam_id}/reviews
```

请求示例：

```json
{
  "decision": "CONFIRM",
  "comment": "与临床观察一致",
  "manual_adjustments": []
}
```

#### 生成报告

```http
POST /api/v1/examinations/{exam_id}/reports
```

## 12. 数据与合规设计

### 12.1 数据分类

| 数据类型 | 示例 | 管理要求 |
|----------|------|----------|
| 患者身份信息 | 姓名、手机号、身份证号 | 严格 RBAC，默认脱敏展示 |
| 医疗数据 | 病史、检验、诊断结论 | 全链路审计 |
| 影像数据 | 眼底图、OCT、热力图 | 原图留存、派生文件可追溯 |
| 模型数据 | 版本、阈值、评估结果 | 只读归档、可回溯 |
| 操作日志 | 登录、审核、签发 | 防篡改、定期备份 |

### 12.2 基础合规要求

- 所有 AI 页面显式展示“辅助诊断参考”
- 报告签发必须由医生触发
- 每份报告必须绑定原始检查、审核记录和模型版本
- 重要操作必须记录操作者、时间、终端和前后状态
- 脱敏数据方可用于算法训练或质控展示

### 12.3 审计事件最小集合

- 登录成功/失败
- 查看患者详情
- 上传或删除图像
- 发起、取消、重跑分析
- 查看 AI 结果
- 审核确认、驳回、修改
- 报告签发、作废、导出

## 13. 验收标准

### 13.1 功能验收

- 可完成患者建档、检查创建、上传、分析、审核、报告、随访完整闭环
- 图像不合格时可明确拦截并提示原因
- AI 结果可查看结构化数据与可视化标注
- 医生审核动作可落库并可追溯
- 报告导出内容与审核结果一致

### 13.2 技术验收

- 所有核心接口提供 OpenAPI 文档
- 异步任务可监控、可重试、可定位失败原因
- 核心对象具备主键、状态字段、创建更新时间
- 审计日志可按患者、检查、报告、用户查询

### 13.3 医疗风险验收

- 页面和报告明确标注辅助诊断性质
- 医生未审核前不得生成正式签发报告
- 结果修改和重检路径清晰可见

## 14. 实施计划

### Phase 1：业务骨架与基础闭环（4 周）

- 完成患者、检查、影像、报告核心数据模型
- 打通上传、质检、异步任务、结果查询闭环
- 完成 Web MVP 页面框架

### Phase 2：AI 集成与审核闭环（4 周）

- 接入眼底彩照分析
- 接入 OCT 分析
- 完成医生审核与报告草稿生成
- 接入基础监控与审计日志

### Phase 3：稳定性与院内试运行（4 周）

- 完成权限矩阵
- 完成随访计划与统计基础能力
- 执行性能压测、异常恢复和数据备份演练
- 启动小规模院内试运行

### Phase 4：临床验证与注册准备（持续）

- 形成回顾性验证数据集
- 沉淀版本变更记录与风险控制材料
- 输出注册申报所需的软件文档基线

## 15. 主要风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 产品范围持续膨胀 | 高 | 明确一期边界，新增需求进入二期池 |
| AI 准确率达不到上线要求 | 高 | 先院内试运行，不直接自动化签发 |
| 图像质量不稳定 | 高 | 建立质量评分与重传机制 |
| 审核流程设计不清 | 高 | 以状态机和审计模型驱动实现 |
| 数据合规准备不足 | 高 | 在一期同步建设审计、脱敏、权限模型 |
| 架构过重拖慢交付 | 中 | 先按最小组件集实施，二期再扩展 |
